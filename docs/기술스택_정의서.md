# 인천항(북항) 3D 해양관제 시스템 — 기술 스택 및 프레임워크 정의서

## 1. 시스템 개요

인천항 북항 해역의 수심, 해류, 선박, 위험구역 등 해양 정보를 3D로 통합 가시화하여 항만 관제 업무를 지원하는 웹 기반 관제 시스템.

## 3. Three.js vs Cesium 비교 분석

### 3.1 Cesium 기반 접근의 한계

본 프로젝트는 초기에 Cesium.js 기반으로 개발을 시작하였으나, 다음과 같은 기술적 한계로 인해 Three.js로 전환하였다.

#### 3.1.1 해저 지형 표현의 제약

| 문제 | 상세 |
|------|------|
| **삼각형 메시 렌더링 불가** | Cesium의 `Primitive` API로 커스텀 삼각형 메시를 생성할 때 셰이더 호환 문제(`compressedAttributes`, `batchId` 등) 발생. per-vertex color를 지원하는 연속 메시를 렌더링할 수 없음 |
| **폴리곤 틈 문제** | 개별 `Entity polygon`으로 격자 셀을 렌더링 시, 인접 셀 간 꼭지점이 공유되지 않아 틈(gap)이 발생. 해저 지형이 조각난 종이처럼 보임 |
| **지형 충돌** | Cesium의 `WorldTerrain`과 커스텀 수심 메시가 높이 기준에서 충돌. glTF로 변환해도 지형에 묻히거나 공중에 뜨는 문제 |
| **볼록 폴리곤 제약** | `Entity polygon`은 볼록(convex) 형태만 지원. 행 단위 리본 폴리곤 시도 시 오목 형태가 깨짐 |

#### 3.1.2 애니메이션 표현의 제한

| 문제 | 상세 |
|------|------|
| **해수면 파도** | Cesium에서 정점 단위 실시간 애니메이션(파도 물결)을 구현할 방법이 없음. Entity나 Primitive 모두 정적 geometry만 지원 |
| **파티클 시스템** | 수천 개 파티클의 실시간 위치 업데이트가 Entity 기반으로는 성능 한계 |
| **해류 벡터** | 유속/유향에 따른 파티클 흐름 애니메이션이 Cesium의 `PolylineArrow`로는 정적 표현에 그침 |
| **오염 확산** | 방사형 확산 + 해류 드리프트 같은 복합 애니메이션이 Cesium에서는 구현이 극히 어려움 |

#### 3.1.3 성능 문제

| 문제 | 상세 |
|------|------|
| **Entity 수 제한** | 수천 개 Entity(수심 셀, 건물, 해류 화살표) 동시 렌더링 시 프레임 드롭 |
| **지구본 오버헤드** | 전 지구 좌표계(ECEF) 변환, 지구본 렌더링 등 로컬 관제에 불필요한 연산 부담 |

### 3.2 Three.js 전환의 장점

| 항목 | Three.js | Cesium |
|------|----------|--------|
| **삼각형 메시** | `BufferGeometry` + vertex color → 19,168개 삼각형 틈 없는 연속 면 | 불가 (셰이더 호환 문제) |
| **파도 애니메이션** | 정점별 실시간 Y 좌표 + 색상 업데이트 (5중 주파수) | 불가 |
| **파티클 (해류)** | `Points` + 실시간 위치 업데이트, GPU 활용 | Entity 기반, 느림 |
| **오염 확산** | 500개 파티클 방사형 확산 + 색상 변화 | 극히 제한적 |
| **카메라 제어** | 완전 자유 (궤도, 패닝, 줌) | 지구본 기반 제약 |
| **성능** | 50만+ 정점 메시도 60fps | 수천 Entity에서 프레임 드롭 |
| **지형 통합** | 육지+해저를 하나의 메시로 자연스럽게 연결 | 불가 (terrain과 충돌) |

### 3.3 Three.js의 제한 사항 및 대응

| 제한 | 대응 방안 |
|------|-----------|
| 지도 타일 직접 관리 필요 | 서버 측 타일 분석 → 지형 메시 생성으로 대체 |
| 위경도 좌표 변환 필요 | `coords.ts` 유틸 모듈로 WGS84 → 로컬 미터 변환 |
| GIS 기능 부재 | 필요 시 Turf.js 등 GIS 라이브러리 연동 가능 |
